## 一、 个人数据统一与时间线归档（4 项）

### 1. karlicoss/promnesia
- **仓库地址**：https://github.com/karlicoss/promnesia
- **1. 核心解决的问题**：人在浏览网页、研究技术或重访历史链接时，经常忘记“我以前在哪儿见过这个页面/概念，当时在聊什么或记过什么笔记”，上下文被割裂在浏览器历史、聊天记录、本地 Markdown、书签等数十个孤岛中。
- **2. 使用的方法**：采用后端源索引器（Sources）+ URL 规范化（Canonical URL Normalization）+ 本地索引数据库（SQLite 形式存储 `Visit` 记录，核心语义围绕 `url`、`dt`、`locator`、`context`、`duration` 等字段）+ 浏览器侧边栏扩展架构，将多源出现记录反查并高亮叠加回当前网页。
- **3. 解决前后的对照**：
  - **Before**：面对一个熟悉却想不起出处的 URL 或术语，只能在 Chrome 历史、Telegram、Obsidian、GitHub Issue 中逐一全文搜索，回忆成本高且往往漏掉当时语境。
  - **After**：打开任意网页即可在浏览器侧边栏实时看到“何时、在哪个聊天/笔记/仓库、附带哪段上下文提及过此链接”，并附带可回跳源文件的 Locator。
- **4. 对「Context 补全计划」的提示与指示**：
  - **Locator 是可信溯源的底线**：我们的 L0/L1 事件模型必须保留可回跳原文件的 `locator`（如音频时间戳范围、网页规范化 URL、文件行号），拒绝“只留摘要丢出处”。
  - **URL 规范化是跨渠道合流的关键**：剪切板复制的 URL、浏览器访问的 URL、聊天粘贴的 URL 必须去追踪参数与归一化，才能与语音或笔记事件自动关联。

### 2. karlicoss/HPI (Human Programming Interface)
- **仓库地址**：https://github.com/karlicoss/HPI
- **1. 核心解决的问题**：个人数据导出格式五花八门（JSON、CSV、SQLite、GDPR 压缩包、专有 API），每次写脚本、做分析或接入 LLM 工具都需要针对不同数据源重复写脆弱的解析代码。
- **2. 使用的方法**：在“先各自导出落盘，不求单一中央大库”的前提下，用标准化 Python 包按模块划分数据源，对上层暴露统一、带类型标注的 Python Iterator / Model 接口（如位置、阅读、浏览器历史、短信/IM 等），并支持叠加层与本地缓存加速。
- **3. 解决前后的对照**：
  - **Before**：每接一个新工具（脚本、搜索、AI 助手），就要重读一遍微信/浏览器/Kindle/GitHub 导出格式文档，历史导出包改版即全部失效。
  - **After**：原始导出包（如 Google Takeout、Telegram Export）只需放进约定目录，上层消费方通过统一的 `my.*` Python 模块流式读取归一化后的事件，消费逻辑与原始格式解耦。
- **4. 对「Context 补全计划」的提示与指示**：
  - **“可替换的统一接口”优于“强制集中入单一闭源库”**：我们的 L0 原始归档保留各渠道原格式与自由扩展字段，L1 再映射为统一的 `ContextEvent` Schema，既保留原始保真度又不阻塞后续扩展。
  - **支持“事后重算”**：因为原始导出与消费接口分离，未来换用更好的分词、说话人识别或摘要模型时，可以从 L0 无损重跑生成新版 L1/L2。

### 3. timelinize/timelinize
- **仓库地址**：https://github.com/timelinize/timelinize
- **1. 核心解决的问题**：多平台个人数字足迹（社交消息、照片 EXIF、位置轨迹、文件记录等）以碎片形态散落，既难以做跨渠道的时间轴回放，也缺少按“同一人/同一天/同一地点”对齐的本地归档软件。
- **2. 使用的方法**：基于 Go 与本地 SQLite/文件存储构建单机多源导入管线（据公开文档与仓库介绍），将各数据源导入为带来源标识、时间戳、实体关系（人物/地点/媒体附件）的统一时间线索引，并提供桌面/Web 时间线视图。
- **3. 解决前后的对照**：
  - **Before**：找某年某月某次出差或聚会的全部线索，需要在相册、地图时间线、聊天导出和文档文件夹之间手动对齐时间。
  - **After**：同一时间窗口内的照片、位置、消息在同一条本地时间轴上交汇呈现，不依赖任何云端厂商续存。
- **4. 对「Context 补全计划」的提示与指示**：
  - **时间轴是所有渠道天然的公共主键**：录音、剪切板、网页阅读、IDE 切换即使内容模态不同，都能先按 UTC 时间戳严密对齐，再做区间聚类。
  - **冷启动导入与增量采集并重**：项目初期既要有实时后台守护进程（如音频/剪切板监听），也要为历史记录留好离线批导入入口。

### 4. Dogsheep
- **项目地址**：https://dogsheep.github.io/
- **1. 核心解决的问题**：个人在 Twitter、GitHub、Hacker News、Pocket、Apple Health、Google Takeout 等服务的数据虽然可下载，但没有轻量工具把它们变成“可直接用 SQL 查询分析的本地数据库”。
- **2. 使用的方法**：由 Simon Willison 发起的工具家族，核心理念是 **“Personal Data Warehouse in SQLite”**——为每个平台写一个独立的 Python 小型 CLI（如 `github-to-sqlite`、`twitter-to-sqlite`、`google-takeout-to-sqlite`），把 API/导出包同步进一个或多个 SQLite 文件，并配合 `Datasette` 立刻获得 Web 检索、全文索引（FTS5）和 JSON API。
- **3. 解决前后的对照**：
  - **Before**：导出的数据躺在硬盘 JSON 压缩包里变成“只写不读的电子坟墓”，想回答一个跨源统计问题要临时写解析脚本。
  - **After**：所有个人历史数据进入标准 SQLite 表结构，两条 SQL 就能完成跨表 Join 查询与全文搜索，且单文件即可备份迁移。
- **4. 对「Context 补全计划」的提示与指示**：
  - **SQLite + FTS5 + 轻量表结构是最适合个人设备的 L1 底座**：无需运维 Postgres/Milvus 等重型基础设施，单文件数据库即可同时服务 CLI、MCP Server 与离线检索。
  - **“一源一小工具 + 合流成库”模式极简可靠**：我们的 `record-for-agent` 录音采集与 `ClipContext` 剪切板采集正符合 Dogsheep 的微采集器哲学。

## 二、 端侧感官与桌面 / 浏览器采集（10 项）

### 5. ActivityWatch (ActivityWatch/activitywatch)
- **仓库地址**：https://github.com/ActivityWatch/activitywatch
- **1. 核心解决的问题**：用户与 Agent 都缺少一条关于“电脑前的时间究竟花在哪个应用、哪个窗口、哪段活跃时段”的客观本地日志，导致无法还原工作会话边界或做时间/注意力复盘。
- **2. 使用的方法**：采用**核心服务器（aw-server，REST API + SQLite 存储 Bucket/Event 模型）+ 多端解耦 Watcher 插件**架构：例如 `aw-watcher-window` 轮询活跃应用名与窗口标题、`aw-watcher-afk` 根据键鼠空闲判定是否 AFK（离开电脑）、`aw-watcher-web` 抓取当前聚焦标签页 URL/标题；相邻相同状态的事件通过 **Heartbeat 合并机制** 压缩为单条带 `duration` 的区间记录。
- **3. 解决前后的对照**：
  - **Before**：每秒轮询会产生海量冗余重复记录，且缺乏 AFK 判定，导致挂机时间被误算进工作上下文。
  - **After**：磁盘只保留紧凑的“应用/窗口聚焦时间段 + AFK 区间”，低功耗后台常驻即可精准还原一天内的连续工作切片。
- **4. 对「Context 补全计划」的提示与指示**：
  - **Heartbeat 合并是防止 L1 事件表膨胀的标准手法**：窗口焦点和网页停留必须用“开始时间 + 心跳续期计算 `duration`”，而不是按秒写死日志。
  - **AFK 检测是“真实上下文”与“挂机噪声”的分水岭**：在剪切板、浏览器与语音通道做 Episode 切分时，AFK 间隙本身就是天然的会话边界信号。

### 6. Maccy (p0deje/Maccy) + 本仓 ClipContext
- **仓库地址**：https://github.com/p0deje/Maccy
- **1. 核心解决的问题**：系统剪贴板默认只保留最后一条复制内容，大量跨应用搬运的代码片段、报错日志、网址、临时段落转瞬即逝；而现有剪切板管理器多面向人工粘贴，不向 Agent 提供结构化接口。
- **2. 使用的方法**：Maccy 通过轻量轮询 `NSPasteboard.changeCount` 监听剪贴板变化，支持忽略敏感应用（如密码管理器 1Password/Bitwarden 等敏感类型标记 `nspasteboard.org`），并本地持久化；本仓配套的 `ClipContext` 在其思路之上，通过 `clipboard.json` 中的 `revision` / SHA-256 指纹与多模态条目，直接暴露 `recent` / `search` / `get` 等 MCP 检索能力。
- **3. 解决前后的对照**：
  - **Before**：复制过一段错误信息或参考段落后，只要再复制一次新内容就永久覆盖，AI 助手完全不知道你刚刚在屏幕间搬运了什么高意图文本。
  - **After**：每一次显式 `Cmd+C` 都成为“用户主动筛选过的高信噪比意图信号”，带来源、时间戳与去重指纹入库，Agent 可随时按时间窗口或关键词回溯。
- **4. 对「Context 补全计划」的提示与指示**：
  - **剪切板是“高信噪比、低体积、零额外认知负担”的首选文本通道**：比全屏截图 OCR 干净得多，往往直接暴露用户此刻最想处理的报错、人名或链接。
  - **安全隔离不可妥协**：必须原生遵守 `nspasteboard.org` 瞬态/机密标记协议与 macOS 15.4+ 剪贴板访问权限规范，密码和敏感凭证绝不落盘。

### 7. Defuddle (kepano/defuddle) & Obsidian Web Clipper (obsidianmd/obsidian-clipper)
- **仓库地址**：https://github.com/kepano/defuddle · https://github.com/obsidianmd/obsidian-clipper
- **1. 核心解决的问题**：直接抓取网页原始 HTML 或全页面 DOM 会混入海量导航栏、广告、推荐列表、页脚和脚本标签，导致存入知识库或喂给 LLM 时 Token 浪费严重且干扰检索精度。
- **2. 使用的方法**：`defuddle` 作为专为现代网页与 Markdown 输出设计的正文提取库，先清理标准非正文区块与冗余样式，并提取结构化 Metadata（作者、发布时间、标题等）后转为干净 Markdown；`obsidian-clipper` 将其嵌入浏览器扩展，结合可配置模板一键将当前网页正文与元数据写入本地笔记库。
- **3. 解决前后的对照**：
  - **Before**：要么保存整个丑陋杂乱的 HTML/纯文本副本，要么把导航栏和“猜你喜欢”也编入向量索引，引发检索污染。
  - **After**：只沉淀纯净、可读、带规范frontmatter 元数据的 Markdown 正文，体积通常大幅缩减且语义密度极高。
- **4. 对「Context 补全计划」的提示与指示**：
  - **采集阶段必须把“读到了什么”与“页面噪声”剥离**：不能简单只存 URL（链接随时会 404 或需要登录），应在确认“有效停留”（例如超过阈值且非隐藏标签页）时调用 Defuddle 级 Extractor 抽取 Markdown 正文做内容指纹去重归档。
  - **Markdown 是 L1 文本载荷的理想载体**：同时适合人类阅读复习、全文检索与大模型 Context 注入。

### 8. Mozilla Readability (mozilla/readability)
- **仓库地址**：https://github.com/mozilla/readability
- **1. 核心解决的问题**：早期网页缺乏统一的 `<article>` 语义标注，不同站点 HTML 结构千差万别，如何稳定地用规则与启发式评分识别一篇网页的主阅读区域成为浏览器阅读模式与网页采集的核心难题。
- **2. 使用的方法**：Firefox 阅读视图背后的独立 JS 库。通过对 DOM 节点（如 `<p>`、`<div>`）统计字数、逗号密度、链接密度、特定正向/负向 class/id 名权重进行启发式打分与父节点冒泡累加，剥离高链接密度区域（边栏/菜单），保留主内容 DOM 树及基础标题/摘要信息。
- **3. 解决前后的对照**：
  - **Before**：针对每个网站手写 XPath/CSS 选择器维护成本极高，网站一改版就崩溃。
  - **After**：用一套通用 DOM 启发式算法覆盖绝大部分文章、博客与新闻页，成为后续几乎所有开源正文抽取工具（包括 Defuddle 的对比基准）的事实标准基线。
- **4. 对「Context 补全计划」的提示与指示**：
  - **“双引擎/可回退的正文提取管线”更稳妥**：在浏览器采集端可优先尝试现代 Markdown 友好型提取（Defuddle），并在复杂旧式长文页面回退或对照 Readability 的结果，保证 L1 网页快照的召回率与纯净度。

### 9. WorldBrain Memex (WorldBrain/Memex)
- **仓库地址**：https://github.com/WorldBrain/Memex
- **1. 核心解决的问题**：普通浏览器书签只记“曾经点过收藏的网址”，无法全文检索“曾经认真读过但没收藏的页面正文”，也缺乏在原网页上直接批注、打标签并与历史阅读联想的工具。
- **2. 使用的方法**：构建浏览器扩展与本地索引引擎（在浏览停留后自动抓正文并建立全文索引，曾采用 IndexedDB/本地存储并演进本地优先同步架构），允许用户为网页片段高亮批注、组织 Space/标签，并直接在任意搜索页或新标签页反查自己历史看过的全部网页正文。
- **3. 解决前后的对照**：
  - **Before**：记住某篇文章“大概讲过某个概念”，但在 Google 重搜换了关键词根本找不回原页面，Chrome 历史只匹配标题和 URL 常常搜不到。
  - **After**：所有深度阅读过的网页都自动纳入个人可检索全文库，支持按内容关键词、域名、时间和个人高亮精确召回。
- **4. 对「Context 补全计划」的提示与指示**：
  - **“自动静默索引 + 主动高亮优先加权”是极佳的混合模式**：绝大多数网页只需静默记录“有效浏览 + 摘要/关键词”，而用户主动高亮、复制或批注的段落应被标为高重要性（`importance`）优先进工作记忆。

### 10. Omi (BasedHardware/omi)
- **仓库地址**：https://github.com/BasedHardware/omi
- **1. 核心解决的问题**：日常生活中大量关键想法、口头约定和面对面交流发生在离开电脑和手机键盘之后，传统录音笔只能留下长达数小时的裸音频文件，回听门槛极高，无法直接转化为行动记忆。
- **2. 使用的方法**：提供开源可穿戴硬件参考设计 + 手机端/桌面端 Companion App + 开源后端与插件生态（据公开项目文档）：持续/按需捕获音频流并做 VAD（语音活动检测）与语音转写，经 LLM 提取会话摘要、待办 Action Items 与个人记忆 Facts，并通过开放 App/Webhook 生态触发自动化工作流。
- **3. 解决前后的对照**：
  - **Before**：线下讨论结束后很快遗忘口头结论，即便录了音也因为几个小时的音频无从定位核心片段。
  - **After**：口语流被自动切分为结构化对话段落、摘要与记忆要点，离开工位后的“离线真实世界语境”得以并入数字大脑。
- **4. 对「Context 补全计划」的提示与指示**：
  - **验证了本仓库重点投入“音频通道（`record-for-agent`）”的前瞻性**：真实语音流是键盘鼠标之外信息密度最高的 Context 增量来源。
  - **后端解耦与“事件触发 + 记忆沉淀”**：Omi 把原始音频流与“转写 -> 事件分割 -> 记忆抽取 -> 插件触发”分成清晰层级，我们的 `record-for-agent` 也应坚持“前端专注低功耗高可靠采集+VAD，后端独立跑 ASR 与结构化对齐”。

### 11. screenpipe (screenpipe/screenpipe) & OpenRecall (openrecall/openrecall)
- **仓库地址**：https://github.com/screenpipe/screenpipe · https://github.com/openrecall/openrecall
- **1. 核心解决的问题**：大量跨软件操作（看视频、看 PDF 扫描件、浏览不开放 API 的封闭桌面/IM 应用）从未落入剪贴板或开放文件系统，传统集成 API 方案存在“视觉盲区”。
- **2. 使用的方法**：以低频定时截屏 + 本地 OCR（以及 `screenpipe` 中可选的本地音频录屏/转写）持续记录屏幕上的文字与窗口状态，写入本地 SQLite（按截图/帧时间、App 名、窗口名、OCR 文本等索引），`screenpipe` 进一步提供 Rust 核心、本地检索 API 与插件生态，`OpenRecall` 则主打纯 Python 的轻量截屏 OCR 历史回放。
- **3. 解决前后的对照**：
  - **Before**：在封闭聊天窗口或视频会议画面里闪过的一行字，只要没手抄或没截图，事后便彻底不可检索。
  - **After**：电脑屏幕上出现过的几乎一切可读文字都能按时间轴或关键词“时光倒流”找回。
- **4. 对「Context 补全计划」的提示与指示**：
  - **屏幕 OCR 只能作“对照组与兜底方案”，绝不能当主采集器**：连续截屏 + OCR 会带来海量重复噪声、较高功耗/磁盘开销以及极高隐私风险（银行卡、私聊同屏暴露），必须谨慎开启。
  - **启发我们的通道分层**：优先用低噪声结构化渠道（音频、剪切板、网页 DOM/Defuddle、Shell/Git、窗口焦点标题），仅在明确授权且无法通过 API 获取的特定场景考虑低频按需视觉辅助。

### 12. Atuin (atuinsh/atuin)
- **仓库地址**：https://github.com/atuinsh/atuin
- **1. 核心解决的问题**：开发者在终端敲过的数万条命令，默认被按行覆盖写入 `.zsh_history` 等纯文本文件，缺乏执行目录、退出码、耗时、主机名和完整时间线，换台机器即失联。
- **2. 使用的方法**：用 Rust 重写 Shell 历史引擎，将每次命令执行作为完整结构化记录写入本地 SQLite 数据库（记录命令文本、时间戳、执行耗时 `duration`、退出码 `exit`、`cwd` 工作目录、`session` 会话 ID 与主机信息），并通过端到端加密实现多设备同步与高速 `Ctrl+R` 交互检索。
- **3. 解决前后的对照**：
  - **Before**：想找“上周在哪个项目目录下跑过一个带特定参数的构建命令且执行成功了”，`history | grep` 无法过滤目录、时间或成功状态。
  - **After**：一条检索即可按目录、退出码 `0`、会话和模糊文本秒级定位，且天然构成了开发者工作流的精准时间轴。
- **4. 对「Context 补全计划」的提示与指示**：
  - **极简但字段完备的事件设计典范**：记录“`command + cwd + exit_code + duration + timestamp`”这 5 个极轻字段，就能让 AI 助手准确推断用户“正在做什么项目、卡在什么报错上、哪些命令有效”。
  - **退出码与耗时就是隐含反馈信号**：失败退出码聚合往往标记着一段排错（Debugging）Episode 的开始，最终成功退出则标记该阶段闭环。

### 13. Dawarich (Freika/dawarich)
- **仓库地址**：https://github.com/Freika/dawarich
- **1. 核心解决的问题**：Google Timeline 等云端位置历史服务逐步转为仅端侧存储或面临关停/迁移风险，用户希望完全自托管（Self-hosted）自己的长期 GPS 轨迹与造访地点历史。
- **2. 使用的方法**：提供可 Docker 自部署的开源位置历史平台，支持从 Google Takeout、OwnTracks、Overland、Home Assistant 等多源导入与持续上报轨迹点，自动聚合访问地（Visits/Places）、里程统计与地图热力回放，并暴露 API 供外部调用。
- **3. 解决前后的对照**：
  - **Before**：地理位置时间线依赖云厂商黑盒控制，不能随心与其他个人日志关联查询。
  - **After**：几十年跨度的个人物理空间移动轨迹全部掌握在自有数据库中，可编程回答“去年 10 月我去过哪里”。
- **4. 对「Context 补全计划」的提示与指示**：
  - **空间（Where）+ 时间（When）是触发人物/事件记忆的强索引**：即使不直接做主传感器，预留 `location` / `place` 作为 L1/L2 可选上下文属性，也能极大增强日记回忆、差旅归档与跨日情景回忆检索。

### 14. FunASR / SenseVoice / sherpa-onnx（本地语音识别技术栈）
- **仓库地址**：https://github.com/modelscope/FunASR · https://github.com/FunAudioLLM/SenseVoice · https://github.com/k2-fsa/sherpa-onnx
- **1. 核心解决的问题**：全天候录音采集如果强依赖云端商业 ASR API，会产生持续高额账单、网络延迟与极端隐私泄露风险（全天对话上传第三方服务器不可接受），而传统离线模型往往中英混读错字连篇、缺标点且缺说话人/情感信息。
- **2. 使用的方法**：
  - `FunASR` 提供端到端语音基础框架（VAD 端点检测 + Paraformer/流式识别 + 标点恢复 PUNC + 说话人分离）；
  - `SenseVoice` 在多语言（尤其高准确率中文及中英混读）之上同时输出语音识别文本、情感标签与音频事件标签（如掌声、笑声、音乐等）；
  - `sherpa-onnx` 基于 ONNX Runtime 提供零依赖 Python/网络、跨 macOS/iOS/Android/嵌入式端侧 CPU 高速推理的统一封装（支持流式与非流式及说话人识别）。
- **3. 解决前后的对照**：
  - **Before**：本地转写慢、无标点、中英夹杂乱码，被迫要么把隐私录音传云端，要么录音积灰不转写。
  - **After**：在 MacBook 或边缘设备上完全离线即可高质量完成“VAD 切片 -> 多语种精准转写 -> 自动标点 -> 音频情感/事件标注”，真正让音频变成零云依赖的实时文本事件流。
- **4. 对「Context 补全计划」的提示与指示**：
  - **直接加固本仓 `record-for-agent` 的技术护城河**：采用 `sherpa-onnx` 或 `FunASR/SenseVoice` 作为离线转写后端，既可保护绝对隐私，又能拿到说话人分段与音频事件信号用于后续事件分割。
  - **端侧分段优先**：先由 VAD 切出活跃语音段再进转写，避免数小时静音空跑大模型。

## 三、 Agent 记忆与 Context 基础设施（5 项）

### 15. OpenViking (volcengine/OpenViking)
- **仓库地址**：https://github.com/volcengine/OpenViking
- **1. 核心解决的问题**：传统平面向量数据库（Flat Vector RAG）缺乏层次感与全局视图，面对海量多源上下文时，容易检索出上下文割裂、缺乏背景锚点的零碎 Chunk，而且每次把整块原文塞进 Prompt 极度消耗 Token。
- **2. 使用的方法**：提出并实现面向 AI Agent 的 **“Context Database / 虚拟文件系统范式（`viking://` URI）”**：把记忆、资源与技能统一映射为层级目录树，并为每个节点维护 **L0（极简摘要）→ L1（概览/大纲）→ L2（全量细节）三层按需加载机制**，检索时先沿目录定位+摘要筛选，再渐进式钻取具体细节并保留检索轨迹。
- **3. 解决前后的对照**：
  - **Before**：RAG 在全局向量池里盲捞 Top-K 片段，要么塞太多原文撑爆上下文、要么丢掉前因后果只剩孤立句子。
  - **After**：Agent 像查阅有序文件系统一样“先看目录摘要（L0/L1），确定相关后再读正文细节（L2）”，兼顾全局视野、低 Token 消耗与可调试的检索路径。
- **4. 对「Context 补全计划」的提示与指示**：
  - **高度契合本项目的核心整合架构（L0→L4 中的 L0/L1/L2 分层加载思想）**：原始音视频、长网页 Markdown、大段终端日志绝不能直接全量塞给 LLM，应为每条 Episode/Artifact 预生成摘要层与索引指针，由 MCP 工具支持“先列表/摘要、再按 ID/时间区间拉详情”。

### 16. Graphiti (getzep/graphiti)
- **仓库地址**：https://github.com/getzep/graphiti
- **1. 核心解决的问题**：传统静态知识图谱和普通向量检索无法优雅处理“现实世界事实随时间不断变化与推翻”（例如用户换了公司、改了技术选型、调整了项目截止日），导致旧记忆与新记忆在召回时发生自相矛盾的幻觉。
- **2. 使用的方法**：构建面向 Agent 的 **双时序感知（Bi-temporal）动态知识图谱引擎**（Zep 的底层开源核心），核心模型为 Episodic / Entity / Community 节点与带有效起止时间区间（`valid_at` / `invalid_at`、以及系统写入时间与事件发生时间双时间轴）的关系边；新事件增量写入时自动识别与旧事实的冲突，将过期边标记失效而非物理删除，检索结合语义、关键词（BM25）与图遍历混合召回。
- **3. 解决前后的对照**：
  - **Before**：把“3 月我在做 A 项目”和“6 月我转做 B 项目”同时存入向量库后，Agent 常把两个时点事实混为一谈，或需要全量重抽整张图谱才能更新。
  - **After**：增量写入即可完成事实状态演进，“过去曾真、现在已失效”的历史与“当前有效”的最新状态同时可追溯可区分。
- **4. 对「Context 补全计划」的提示与指示**：
  - **个人上下文是强时效演化流，而非静态百科**：项目进度、待办状态、人际分工都在周级甚至日级变化，L3 实体图谱关系边必须带 `valid_from` / `valid_to` 或状态覆盖标记（并参照 STALE 基准对过期知识显式处理）。
  - **混合检索优于纯向量检索**：精确人名、文件名和专有名词靠 BM25 + 图邻接，模糊语义再叠加向量。

### 17. Mem0 (mem0ai/mem0 & mem0-chrome-extension)
- **仓库地址**：https://github.com/mem0ai/mem0
- **1. 核心解决的问题**：对话式 AI 应用每次新开会话即“失忆”，直接把历史全部对话塞入 Context 成本过高且很快触顶，而缺乏冲突合并的简单抽记忆方案会导致记忆条目无限膨胀且前后打架。
- **2. 使用的方法**：设计了 **Extract → Update（`ADD` / `UPDATE` / `DELETE` / `NOOP`）两阶段增量记忆管理管线**，结合向量库、可选 KV 与图记忆（Mem0g），对每轮对话提取候选事实后，检索 Top-K 既有相似记忆交由 LLM 判断执行新增、合并更新、逻辑删除还是无操作；此外生态中的 `mem0-chrome-extension` 直接拦截用户在 ChatGPT / Claude / Perplexity 等主流网页 AI 的提问，注入跨平台个人记忆实现多助手记忆共享。
- **3. 解决前后的对照**：
  - **Before**：用户在 ChatGPT 讲过的个人偏好、项目背景，切到 Claude 或新会话就要重新复制粘贴说明一遍；记忆库若只增不删则会迅速腐化。
  - **After**：记忆以极精简事实条目动态维护更新（减少长期 Token 开销），且通过浏览器扩展/MCP 把“个人记忆层”从单一模型厂商手中剥离出来共享。
- **4. 对「Context 补全计划」的提示与指示**：
  - **跨 AI 工具的“个人统一外挂记忆层”正是本项目的核心落地场景之一**：用户每天在本地 IDE、Claude、ChatGPT、飞书等多个 AI 间切换，记忆必须掌握在用户自己手里并能多端注入。
  - **写时整理（Write-time Consolidation）必须有限度且可回溯**：`ADD/UPDATE/DELETE` 非常适合整理 L3 个人画像事实，但执行 `UPDATE/DELETE` 前必须保留指向 L0/L1 原事件 ID 的溯源链，避免 LLM 误删原始真相。

### 18. Letta (letta-ai/letta)
- **仓库地址**：https://github.com/letta-ai/letta
- **1. 核心解决的问题**：传统 LLM 只是无状态推理函数，被动等待外部 RAG 往固定窗口里填东西，遇到上下文溢出或需要长程自我修正时，模型自己没有任何掌控自己记忆的能力。
- **2. 使用的方法**：源自 MemGPT 论文思想，将操作系统分页虚拟内存理念引入 Agent 运行时：**把上下文明确划分为 Context Window 内的 Core Memory（常驻核心人格与关键用户区块）+ 可调用工具自主读写的外部 Recall Memory（历史对话检索）与 Archival Memory（长期档案库）**，赋予 Agent `core_memory_replace`、`archival_memory_insert/search`、`conversation_search` 等工具调用权，让 Agent 自主管理“换入/换出”和自我编译记忆。
- **3. 解决前后的对照**：
  - **Before**：外部编排脚本死板塞入固定 Top-5 Chunk，上下文不够就硬截断，Agent 无法主动去“翻旧账”或“改写自己的核心认知”。
  - **After**：Agent 从被动受控于固定窗口，转变为可跨数百回合长周期运行、主动检索与维护自身记忆系统的有状态智能体。
- **4. 对「Context 补全计划」的提示与指示**：
  - **区分“始终挂载的工作台（Hot Context）”与“按需翻阅的深水档案库（MCP Tools）”**：本计划产出的 MCP Server（`recent` / `search` / `get_episode` / `trace`）本质上就是给任何外部 Agent（Claude Code、Cursor、Letta 等）提供统一的 Recall & Archival 接口。
  - **支持多轮按需下钻**：单次检索没找全时，允许 Agent 按时间窗继续翻相邻前后的事件，而不是“一锤子 RAG 决定生死”。

### 19. cognee (topoteretes/cognee)
- **仓库地址**：https://github.com/topoteretes/cognee
- **1. 核心解决的问题**：将非结构化个人文档、聊天与代码构建成同时具备“向量语义 + 知识图谱结构”的记忆系统往往需要繁琐的定制 ETL 与胶水脚本，而且管线难以针对不同数据类型复用与扩展。
- **2. 使用的方法**：采用基于异步 **ECL（Extract-Cognify-Load）数据流管线** 的开源框架：以 `DataPoint` Pydantic 模型作为统一扩展原语，先后完成原始数据摄取（支持 30+ 数据源）→ 分块、实体/关系抽取与摘要 Cognify 加工 → 同时写入网络图库（NetworkX/Kuzu/Neo4j 等）与向量库（LanceDB/Qdrant/PGVector 等），并提供统一图+向量多种检索模式（`SearchType`）。
- **3. 解决前后的对照**：
  - **Before**：自己拼装 LangChain + 手写抽取 Prompt + 分别同步图库与向量库，代码脆弱且换库代价大。
  - **After**：几行异步任务流水线即可把杂乱文档沉淀为可同时跑向量相似度与图谱多跳关系推理的双模记忆底座。
- **4. 对「Context 补全计划」的提示与指示**：
  - **“可插拔异步管线（ECL）”设计思路值得 L2→L3 加工层借鉴**：采集与入库（L0/L1）要极快、不依赖重推理；实体关系抽取与摘要（Cognify / L2-L3）则放在异步后台空闲批处理队列里跑，彻底解耦实时采集与重计算。

## 四、 主动式个人上下文与“第二大脑”应用（5 项）

### 20. MineContext (volcengine/MineContext)
- **仓库地址**：https://github.com/volcengine/MineContext
- **1. 核心解决的问题**：多数记忆工具只是“你问我才答”的被动搜索引擎，用户在日常忙碌中不知道自己刚刚遗漏了什么待办、哪些零散屏幕/文件上下文已经足以凑成今日日报或行动建议。
- **2. 使用的方法**：定位为“主动式上下文感知 AI 伙伴”（Proactive Context-Aware AI Partner），持续采集本地截屏/文档等多模态日常活动切片（经筛选压缩后形成结构化 Context 卡片），结合生命周期整合策略自动归纳出**日报总结、待办建议（Todo）、工作流提示与主动信息推送**，同时保留本地可控视图。
- **3. 解决前后的对照**：
  - **Before**：每天下班前对照一堆混乱标签页和聊天记录痛苦回忆“今天做了什么”，重要碎片只在需要写周报时才发现已遗忘。
  - **After**：系统在后台默默完成碎片聚合，下班时已自动躺着一份有事件依据的每日进展与待办提醒。
- **4. 对「Context 补全计划」的提示与指示**：
  - **L4 主动推送（Proactive Context）是终端价值的重要出口，但应建立在高质量 L1/L2 结构之上**：我们与 MineContext 的差异化定位在于“先做好低噪声多传感融合协议与开放基座（音频+剪切板+浏览器等）”，再在其上自然衍生每日简报与主动提醒，而不是一开始被全屏截屏的高消耗绑架。

### 21. Khoj (khoj-ai/khoj)
- **仓库地址**：https://github.com/khoj-ai/khoj
- **1. 核心解决的问题**：个人知识常分散在 Obsidian Markdown、Notion、PDF 与日常临时对话中，需要一个“既能离线私有部署连接本地 LLM，又能一键联网研究并在日常定时自动执行个人任务”的私人 AI 中枢。
- **2. 使用的方法**：提供可自托管的个人 AI 助手平台（支持连接本地 Ollama/LlamaCpp 模型或主流云模型）：多格式文档自动增量建索 + 语义检索 + 多种入口（Obsidian 插件、Emacs、Web、桌面端、WhatsApp/Telegram）+ 自定义 **Automations（定时/条件自动化 Research/推送）** 与 Agents。
- **3. 解决前后的对照**：
  - **Before**：笔记库只是静态文件系统，搜索靠关键词精确匹配，日常情报收集每天都要人工重复发起对话。
  - **After**：私有笔记随时可通过自然语言多客户端对话检索，高频回顾与简报动作交由定时自动化后台完成。
- **4. 对「Context 补全计划」的提示与指示**：
  - **多入口（Client）+ 自动化任务（Automation）增强留存**：即便底层记忆底座很强，也必须让用户能从自己日常习惯的工具（如 IDE MCP、浏览器、CLI、飞书/IM 或每日小结）无摩擦调用；定时回顾（Nightly/Weekly Synthesis）是天然的 L2/L3 夜间巩固窗口。

### 22. Second-Me (mindverse/Second-Me)
- **仓库地址**：https://github.com/mindverse/Second-Me
- **1. 核心解决的问题**：如果完全依赖临时 Prompt 检索（RAG）来模拟“我是谁”，模型往往只记得单点事实却缺乏整体思维习惯、价值观、表达风格与内在关联记忆；同时用户担心把全量个人人格托管给中心化平台。
- **2. 使用的方法**：提出在本地训练并运行属于个人的 **AI Self（L0→L1→L2 分层个人记忆建模与微调框架，HMM 分层记忆建模 + Me-Alignment 算法）**，将个人笔记、对话与历史记录转化为结构化事实与个人认知偏好，甚至微调本地轻量化模型以承载个体“数字分身”，并探索去中心化数字身份交互网络。
- **3. 解决前后的对照**：
  - **Before**：AI 助手只是带着几段零散外挂检索结果的冷冰冰通用模型，不懂用户的表达语调与长期隐含偏好。
  - **After**：沉淀出一个高度对齐个人经历、表达癖好且可控部署在本地的持久化“数字分身”。
- **4. 对「Context 补全计划」的提示与指示**：
  - **明确路线边界：“阶段一重检索与结构化协议，慎用早期全量权重微调”**：对于快速变化的工作流与日常事实（今天修的 Bug、下午开的会），微调滞后且易产生不可控幻觉，**时间线 + 图谱 + RAG/MCP 仍是 L1–L3 主力**；只有在积累数月以上稳定高频风格与核心偏好之后，才值得借鉴其个人对齐/长期偏好建模层。

### 23. personal-ai-memory (marswangyang/personal-ai-memory)
- **仓库地址**：https://github.com/marswangyang/personal-ai-memory
- **1. 核心解决的问题**：普通个人用户只想找一个轻量、私有、无需庞大运维成本的方式，把自己用过的 Chrome 浏览记录和本地记忆整合进日常 AI 对话，但市场上的企业级记忆框架往往部署过重。
- **2. 使用的方法**：主打“浏览器扩展 + 本地私有记忆存储与检索后端”的轻量化开源探索方案（据此前调研记录），将网页浏览上下文与个人记忆碎片抽取存储后，通过检索接口补充给个人 AI 会话。
- **3. 解决前后的对照**：
  - **Before**：个人浏览轨迹与大模型对话完全断开，每次聊起刚看过的资料都要人工复制整页文本。
  - **After**：轻量化浏览器信号与个人本地记忆池打通，AI 对话具备最近浏览过的背景感知。
- **4. 对「Context 补全计划」的提示与指示**：
  - **“轻量开箱可用（Low Friction）”决定了个人开源项目能否活下来**：很多个人记忆项目死于需要同时配置 Docker + Neo4j + Qdrant + RabbitMQ；我们的基准 MVP 必须做到单机 SQLite + 简洁采集脚本 + 标准 MCP，五分钟即可在 Mac 上跑通。

### 24. web-recap (robzolkos/web-recap) & Reading-Watch-List-Extension-Local-LLM (swetas7/Reading-Watch-List-Extension-Local-LLM)
- **仓库地址**：https://github.com/robzolkos/web-recap · https://github.com/swetas7/Reading-Watch-List-Extension-Local-LLM
- **1. 核心解决的问题**：大量“开了就关”的浏览页签和“待读列表（Reading List）”越攒越多却没人看，事后既忘了读过什么，也懒得逐篇回顾摘要。
- **2. 使用的方法**：一类面向浏览器历史聚合回顾与上下文汇总（`web-recap`），另一类结合 Chrome 扩展捕获待读/浏览网页正文后直接调用**本地 LLM（如 Ollama）**做离线摘要、主题分类与推荐（`Reading-Watch-List-Extension-Local-LLM`），避免全文上传云端模型。
- **3. 解决前后的对照**：
  - **Before**：浏览器开上百个 Tab 产生“信息松鼠症”，稍后阅读列表沦为黑洞，一天下来完全说不清在线浏览的收获。
  - **After**：无需额外操作且数据不出本地，即可自动获得当日浏览轨迹与待读清单的结构化主题摘要。
- **4. 对「Context 补全计划」的提示与指示**：
  - **本地 LLM 在“浏览摘要与噪音过滤”环节性价比极高**：用轻量化本地模型做网页初筛（判定是不是无价值广告/工具页、提炼 2 句摘要）完全够用且零 API 成本，可与我们计划中的“有效停留三层判定”直接串联。
