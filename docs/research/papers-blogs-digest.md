## 一、 连续生活流（Lifelog）与 Agent 长期记忆评测论文（7 篇）

### 1. LifeDialBench
- **文献标识**：`arXiv:2604.11182` · https://arxiv.org/abs/2604.11182
- **1. 核心解决的问题**：现有对话记忆基准大多只有纯聊天文本，缺乏人在真实生活中的**跨模态被动生活流上下文**（视觉/日程/健康/位置/语音等 Lifelog 信号与主动对话交织），无法衡量 Agent 在真实长期日常陪伴下的记忆检索与推理能力。
- **2. 使用的方法**：构造多模态长期 Lifelog + 多轮对话联合评测基准，把异构生活流记录与长期对话时间线绑定，从多维度记忆能力（如信息提取、跨模态关联、多跳时序推理、知识更新等）系统评估不同记忆策略（RAG、摘要、结构化存储等）。
- **3. 解决前后的对照**：
  - **Before**：记住几段两人纯文本闲聊就能刷高分，一放到“结合昨天行程、录音与网页记录回答今天问题”的真实多源场景便迅速失灵。
  - **After**：建立了更接近真实个人工作/生活状态的 Lifelog 对话评测坐标系，暴露出单一平面 RAG 在跨流、多跳、时间锚点上的真实瓶颈。
- **4. 对「Context 补全计划」的提示与指示**：
  - **音频与剪切板必须与工作流交叉对齐，不能孤立做检索**：真实问题的答案往往横跨“语音提到的专有名词 + 当时剪贴板复制的链接 + 正在看的浏览器页面”，L2 Episode 聚合必须跨通道联合聚类。
  - **需要为本仓建立“个人基准回放集”**：后续迭代检索策略时，应借鉴其跨流测试题型构造脱敏 Eval 集，而不是只凭体感测试。

### 2. STALE
- **文献标识**：`arXiv:2605.06527` · https://arxiv.org/abs/2605.06527
- **1. 核心解决的问题**：长期个人记忆系统会不断积累曾经真实、但现在已经失效的事实（旧地址、已取消的计划、重构前的设计结论、离职前同事的职责），传统基准几乎不测“**如何识别并抑制过时记忆（Memory Staleness）**”。
- **2. 使用的方法**：专门围绕知识/状态随时间演化（变更、撤销、替代、衰减）构造评测任务，区分最新有效状态、历史状态回忆与明显冲突过时信息，对比简单追加检索与带显式状态覆盖/时效感知机制的表现。
- **3. 解决前后的对照**：
  - **Before**：向记忆库不停 Append“周一改周三”、“选方案 A”后“改选方案 B”，语义相似度一样高，大模型很容易被旧记录误导甚至输出折中幻觉。
  - **After**：量化暴露了纯向量相似度检索在“状态变更场景”的系统性缺陷，把**有效区间（Validity Interval）与状态覆写**推成记忆系统必选项。
- **4. 对「Context 补全计划」的提示与指示**：
  - **区分“历史不可篡改（L0/L1）”与“当前真相可演进（L3）”**：原始事件只追加不销毁，但面向 Agent 问答的 L3 知识条目与状态边必须带 `valid_from` / `valid_to` / `superseded_by` 与时间衰减权重，明确标注某条事实“是否仍有效”。

### 3. PM-Bench
- **文献标识**：`arXiv:2607.12385` · https://arxiv.org/abs/2607.12385 · https://github.com/genglinliu/PMBench （注：`2607.12385` 号码在采集期单一检索结果中出现，引用前可再复核精确发布信息）
- **1. 核心解决的问题**：早期个人记忆评测偏重短对话事实提取，对于长周期个人多源事件中的偏好漂移、习惯归纳与跨时间长尾记忆缺乏对应评测工具。
- **2. 使用的方法**：构建面向个人长期记忆（Personal Memory）的多场景评测数据集与评估框架（配套开源仓 `PMBench`），检验记忆系统在长期个人事件流中的组织、压缩与个性化召回质量。
- **3. 解决前后的对照**：
  - **Before**：只测“用户喜欢喝什么咖啡”的玩具样本，难以考验生产环境中成千上万条碎片事件的筛选能力。
  - **After**：提供贴近个人助理持久记忆需求的系统化验证抓手，凸显仅靠单一重排模型无法弥补早期写入切分粗糙的短板。
- **4. 对「Context 补全计划」的提示与指示**：
  - **写入端结构化决定上限**：评估记忆不能只调检索 Top-K 或 Prompt，更应评估 L1→L2 阶段切分出来的 Episode 边界是否干净、标签与实体抽取是否稳定。

### 4. MemoryCD
- **文献标识**：`arXiv:2603.25973` · https://arxiv.org/abs/2603.25973
- **1. 核心解决的问题**：连续输入环境中，记忆随着时间不断增长，既面临**冲突与矛盾检测（Conflict / Contradiction）**，也面临长期运行后冗余记忆膨胀导致的检索退化，很多基准只测静态库而不测动态演进过程。
- **2. 使用的方法**：提出围绕连续对话/持续记忆流的动态基准与机制分析框架，重点考察系统在记忆持续追加、冲突更新与长程维持下的抗退化能力。
- **3. 解决前后的对照**：
  - **Before**：前 100 条记忆准确率很高，积累到数千条混入矛盾修改后准确率断崖式下降。
  - **After**：明确衡量了连续写入场景下冲突消解与记忆维护策略（写入整理、去重合并、冲突检测）的必要性。
- **4. 对「Context 补全计划」的提示与指示**：
  - **引入“写入/巩固双阶段”**：剪切板重复复制同一报错、同一网页多次切换阅读、会议中反复确认同一决定，必须在 L1 靠内容指纹合并去重，在 L2/L3 靠夜间批处理巩固与冲突消解，防止记忆库信噪比随使用天数递减。

### 5. From Memory to Action
- **文献标识**：OpenReview（采集阶段确认收录于 OpenReview；暂未核验到 arXiv 编号）
- **1. 核心解决的问题**：多数记忆评测只考核“Agent 能不能把过去发生的事**背出来（Recall QA）**”，却不考核“记忆是否真正帮助 Agent **在多步工具调用或决策中做出更正确的行动（Action）**”。
- **2. 使用的方法**：设计需要依赖过往交互记忆与用户偏好的下游行动任务，直接以**任务完成率、工具选择准确性与动作效率**来检验记忆组件的有效性，而不只是文本问答 BLEU/LLM-Judge 分数。
- **3. 解决前后的对照**：
  - **Before**：许多记忆方案为了 QA 刷分把大量无关背景硬塞进 Context，反而干扰了当前工具参数判断与执行焦点。
  - **After**：迫使记忆检索从“回忆录模式”转向“决策辅助（Context Instrumentality）”模式：只呈递对下一步行动真正在场的上下文。
- **4. 对「Context 补全计划」的提示与指示**：
  - **正中本项目命名的核心思想——Instrumentality（工具性/效用导向）**：采集与记忆的终极标准不是“存得多全、复述得多好听”，而是**接到 Claude Code / IDE / 日常 Agent 上时，能否少问用户十句重复背景、一次性把代码或任务做对**。

### 6. LongMemEval
- **文献标识**：`arXiv:2410.10813` · https://arxiv.org/abs/2410.10813
- **1. 核心解决的问题**：以往长上下文评测偏重“大海捞针（NIAH）”式纯文本复制，无法检验现实聊天中跨越极长交互历史、需要**多会话汇总、时间推算、知识更新及拒绝回答不存在信息（Abstention）**的长期交互记忆能力。
- **2. 使用的方法**：构造规模可控但交互轮次极长的真实风格多会话评测基准，覆盖五大核心能力维度：单会话/多会话信息提取与跨会话推理、**知识更新（Knowledge Update）**、**时间推理（Temporal Reasoning）** 与 **弃权拒答（Abstention，不胡编不存在的记忆）**，并系统测试不同索引粒度（轮次级、会话级、Fact 级）与检索增强手法。
- **3. 解决前后的对照**：
  - **Before**：只测大模型一次读 10 万字能不能找出某句话，忽略了实际助手要在数周上百次碎会话里“分清先后、认出更新、不懂就说不知道”。
  - **After**：成为当下开源记忆引擎（如 Zep、Mem0 等）最核心的标尺之一，实证了**索引结构优化、时间戳显式化与检索后重排（Rerank）**对长程记忆的显著收益。
- **4. 对「Context 补全计划」的提示与指示**：
  - **显式标注每条 Context 的时间戳与相对顺序**：纯文本 chunk 不带精确 `occurred_at` 会导致时间推理全面崩盘；MCP 返回结果必须结构化附带绝对时间与相对时间差。
  - **守住 Abstention（知之为知之）原则**：我们的 MCP 检索应清晰返回空结果或低置信标记，并附原始源指针，绝不在 L2/L3 摘要阶段无中生有补脑细节。

### 7. LoCoMo
- **文献标识**：`arXiv:2402.17753` · https://arxiv.org/abs/2402.17753
- **1. 核心解决的问题**：传统对话评测只有几十轮、单一会话，既缺少跨越数十个时间分散会话的长程连续对话，也缺乏多模态内容与结构化的长期事件因果链检验。
- **2. 使用的方法**：采用 LLM + 人物设定/动态事件图驱动并经人工精细校验，生成跨越超长跨度（数百轮、多达数十个独立 Session）的多模态长对话数据集，评估单跳事实、多跳关联、时间推断、开放摘要等不同记忆查询类型。
- **3. 解决前后的对照**：
  - **Before**：对话记忆研究缺乏长周期标准沙盒，模型靠长窗口硬吞全历史似乎勉强够用，掩盖了窗口溢出与推理退化问题。
  - **After**：揭示了即便放进超长上下文窗口，多跳归纳与跨事件时间线对齐依然大幅落后人类水平，推动了事件摘要与层级记忆架构的兴起。
- **4. 对「Context 补全计划」的提示与指示**：
  - **多源汇总不能只靠单跳语义相似度**：找“这周我在语音和网页里围绕同一方案讨论过哪几次”，本质是多跳与时序聚集查询，要求底层同时具备**时间窗口切片 + 实体/主题关联图 + 分层摘要**。

## 二、 事件分割、情景记忆与系统架构论文（6 篇）

### 8. EM-LLM
- **文献标识**：`arXiv:2407.09450` · https://arxiv.org/abs/2407.09450
- **1. 核心解决的问题**：处理几乎无限长的连续文本/交互流时，固定长度滑窗（Sliding Window）或按固定 512 Token 机械切分会把完整语义动作腰斩，导致检索碎片化、丢头少尾且极度低效。
- **2. 使用的方法**：受人类认知心理学**事件分割理论（EST）**启发，将连续输入流先基于模型预测**意外度 / 惊喜值（Bayesian Surprise / 预测误差峰值）**结合注意力图论边界精修（Boundary Refinement）自适应切分为自然 **Episodic Events**，再以两阶段记忆检索（向量初筛相似度 + 邻接上下文时空连续性拓展）回填工作窗口，无需额外微调模型权重。
- **3. 解决前后的对照**：
  - **Before**：固定字数硬切分把一段连续讨论切成好几截无头无尾的块，向量检索经常命中半句话。
  - **After**：事件边界对齐语义转折点，“相邻片段连续召回”恢复了完整上下文叙事感，显著改善长流问答连贯性。
- **4. 对「Context 补全计划」的提示与指示**：
  - **彻底否定 L1→L2 阶段的“机械按固定分钟/固定 Token 切块”**：我们的录音转写流与浏览器事件流不能简单每 5 分钟切一刀，而应结合**静默/AFK 间隙 + 话题向量突变/实体切换/窗口切换**动态确定 Episode 边界。
  - **支持“前后相邻扩展检索”**：MCP 应提供 `get_episode_neighbors` 或按上下文窗口前后延展拉取相邻事件的能力。

### 9. Episodic Memory is the Missing Piece for Long-Term LLM Agents
- **文献标识**：`arXiv:2502.06975` · https://arxiv.org/abs/2502.06975
- **1. 核心解决的问题**：当前绝大多数 LLM 记忆系统混为一谈——把“情景经验”全部强行压扁成静态“语义事实（Semantic Facts）”或零散向量碎片，导致 Agent 失去了人类独有的**单次亲历情景记忆（Episodic Memory：特定时间、地点、过程与上下文结果）**，难以从具体经验中反思演化与避免重蹈覆辙。
- **2. 使用的方法**：作为立场与设计框架论文，从认知科学对比角度辨析**语义记忆、情景记忆与程序记忆**的本质差异，提出面向长期智能体的情景记忆核心属性（空间-时间锚点、上下文不可替代细节、事件序列完整性、与语义记忆分离但双向巩固联动）。
- **3. 解决前后的对照**：
  - **Before**：记忆库里只剩“用户倾向用 Rust”、“某年改过数据库”这种去语境干瘪陈述，追问“当时是怎么一步步排查出来的”完全答不上来。
  - **After**：从理论顶层确立了“**情景档案（Episode Log）与语义知识（Knowledge/Graph）必须分层并存、不可互相替代**”的设计准则。
- **4. 对「Context 补全计划」的提示与指示**：
  - **直接塑造了本项目的 L2（Episode）与 L3（Knowledge/Entity）分层决策**：绝不能在抽取出 L3 个人画像与图谱后就把 L1/L2 原始对话与操作情景删掉或压成一句干瘪总结；**“什么时候在哪儿因为什么改了什么”的过程细节永远靠 L2 Episode 承载**。

### 10. Zep
- **文献标识**：`arXiv:2501.13956` · https://arxiv.org/abs/2501.13956
- **1. 核心解决的问题**：在企业与个人 Agent 对话交互中，只靠静态文档分块向量检索既丢失实体之间的多跳结构关系，又无法精确记录事件随时间演进的动态有效性，且常受困于高延迟检索。
- **2. 使用的方法**：围绕其开源引擎 **Graphiti** 提出三层时序感知知识图谱架构：**Episode 子图**（原始对话与消息事件原文保真节点）→ **Semantic Entity 子图**（带双时序 `t_valid` / `t_invalid` 等状态区间的实体与边，写时增量识别冲突并使旧边失效）→ **Community 子图**（高层簇摘要），并通过多路径混合检索（语义向量 + BM25 + 图邻接遍历 + RRF/多种重排）低延迟组装 Context。
- **3. 解决前后的对照**：
  - **Before**：平铺记忆基线在时间变化、多跳推理与跨会话综合测试上准确率偏低，且全历史进窗口耗时与 Token 成本过高。
  - **After**：在不塞入全量对话历史的前提下，既能精确回答当前生效的复杂关联事实，又通过轻量按需图检索显著压缩上下文 Token 消耗与延迟。
- **4. 对「Context 补全计划」的提示与指示**：
  - **可溯源的三层子图（Episode → Entity → Community）是 L2/L3 的绝佳落地范式**：每个抽取出来的实体结论边都能顺着指针查回对应的原始 Episode，兼顾推理深度与事实可查验。
  - **异步写入保障交互不卡顿**：知识抽取与冲突判别不必阻塞前端采集/对话，交由后台异步管线完成。

### 11. Mem0
- **文献标识**：`arXiv:2504.19413` · https://arxiv.org/abs/2504.19413
- **1. 核心解决的问题**：直接把日益膨胀的完整历史会话塞进长窗口 LLM 推理既昂贵又高延迟，而普通静态 RAG 不擅长对持续涌入的碎片化新陈述做紧凑的增量维护（合并、更新、淘汰）。
- **2. 使用的方法**：系统提出并对比纯向量记忆（Mem0）与图增强变体（`Mem0g`）：通过两阶段流水线——先结合近期上下文与会话摘要抽取显著候选事实，再经由工具调用或 LLM 控制器比对库内相似记忆，在 **`ADD` / `UPDATE` / `DELETE` / `NOOP`** 四种操作间做出原子决策，持续维持一个极高密度的精简个人事实池；并在 `Mem0g` 中把实体三元组同样引入图关系维护。
- **3. 解决前后的对照**：
  - **Before**：完整对话全文进上下文每次推理成本高昂、P95 延迟高；简单 Append 向量库则充满重复与自相矛盾记录。
  - **After**：显著降低了每次回答所需输入 Token 体积与端到端检索生成延迟，同时在长对话基准上取得了优于朴素基线的记忆准确率与更新一致性。
- **4. 对「Context 补全计划」的提示与指示**：
  - **高性价比“工作记忆卡片”维护机制**：可用于维护本项目中最高层（L3 个人状态与稳定偏好清单），显著减轻注入给 IDE/聊天 Agent 的默认 Prompt 负担。
  - **警惕单向破坏性更新**：`Mem0` 面向事实条目做原地 `UPDATE/DELETE` 在对话场景很省空间，但在个人 Lifelog 归档场景绝不能让 LLM 直接覆盖掉 L0/L1 原事件；L3 的更新必须作为“新版本视图”并附源事件引用。

### 12. Nemori
- **文献标识**：`arXiv:2508.03341` · https://arxiv.org/abs/2508.03341 （注：标题与 arXiv ID 的精确对应关系在调研阶段为部分核验状态）
- **1. 核心解决的问题**：当前许多记忆系统把记忆整理做成死板的机械周期总结，忽略了人类记忆如何按自然事件切分并不断“带着预测误差去对齐与演化认知”的自组织特性。
- **2. 使用的方法**：同样从认知科学寻找灵感，探索将自适应情景边界划分（Boundary Alignment / Episode Segmentation）与基于认知预测偏差的记忆演化对齐原则（Predict-Calibrate 类自组织思路）融入智能体长期记忆构建流程。
- **3. 解决前后的对照**：
  - **Before**：只做盲目压缩摘要会导致新信息与旧认知反复重复记录或丢失真正意外的新转折。
  - **After**：将注意力与存储容量集中到“超出已有预期的真正信息增量”上，提高长期情景记忆的组织紧致度。
- **4. 对「Context 补全计划」的提示与指示**：
  - **“惊喜度 / 信息增益过滤”可用于压缩冗余通道信号**：每天浏览器切 500 次重复页面、电脑挂机数小时几乎没有信息增益；只有状态变化、未见过的新实体、意外报错和决策转折点才配触发重计算或进入高权重记忆。

### 13. Memory for Autonomous LLM Agents
- **文献标识**：`arXiv:2603.07670` · https://arxiv.org/abs/2603.07670
- **1. 核心解决的问题**：Agent 记忆研究方向众多（RAG、图谱、微调、长上下文、OS 内存模拟等），工程与学术界缺乏统一的形式化语言来比较不同方案到底解决了什么、漏掉了什么。
- **2. 使用的方法**：作为 2026 年全面综述，采用部分可观测马尔可夫决策过程（**POMDP**）视角对智能体记忆进行统一形式化抽象，将所有五花八门的记忆机制归纳进 **Write（写入编码）– Manage（维护演化/遗忘整合）– Read（按需检索与注入）** 三轴生命周期，系统拆解记忆载体、表示形式、更新机制与典型评测体系。
- **3. 解决前后的对照**：
  - **Before**：设计个人记忆架构时容易陷入“只堆向量库还是非要上知识图谱”的局部工具争论，忽视了写入过滤与维护遗忘环节。
  - **After**：给出了清晰的全链路设计地图——Write 决定信息保真度与噪音下限，Manage 决定长期不腐化，Read 决定当下对任务是否有用。
- **4. 对「Context 补全计划」的提示与指示**：
  - **用 `Write – Manage – Read` 三轴审查本项目每一层模块**：
    - `Write`：多渠道低摩擦采集与 L1 去重（`record-for-agent` + `ClipContext` + Defuddle/Readability + ActivityWatch）；
    - `Manage`：L2 Episode 边界聚合 + 后台异步汇总 + L3 双时序状态演进与垃圾压缩；
    - `Read`：面向真实 Agent 工具调用的分层检索 MCP（L0/L1/L2 按需下钻）+ 严格时效过滤。

## 三、 经典奠基文献（3 篇）

### 14. Personal Knowledge Graphs: A Research Agenda
- **文献标识**：Balog & Kenter, *ICTIR 2019* · `DOI:10.1145/3341981.3344241` · https://dblp.org/rec/conf/ictir/BalogK19
- **1. 核心解决的问题**：在现代 LLM 爆火之前，知识图谱研究主要面向全人类通用百科（如 Wikidata、Google Knowledge Graph），完全缺乏关于“**以‘我（User）’为中心节点、融合个人私有与公共实体**”的系统性定义与研究纲领。
- **2. 使用的方法**：正式界定 **个人知识图谱（PKG）** 的概念、四大核心特征（**个人中心视角、多源私有+公共链接、结构化实体关系、随时间动态演化**）以及构建、融合与个性化服务的完整研究议程。
- **3. 解决前后的对照**：
  - **Before**：个人文件、联系人、兴趣和日程被当作各自孤立的表或文本目录，无法“以我为中心”建立实体关系连接（“张三 — 我同事 — 负责的 Project X — 昨天开的评审会”）。
  - **After**：奠定了后来所有个人 AI 记忆、个人图谱引擎（包括 Graphiti / 个人第二大脑）的清晰理论坐标系。
- **4. 对「Context 补全计划」的提示与指示**：
  - **所有零散渠道最终都要向“以用户（User）为原点的个人图谱与实体主键”收敛**：同一个人名在录音转写（声纹/称呼）、剪切板邮件地址、IM 账号和日程里必须归并为同一个 `Person` 实体锚点，这是打通跨渠道 Context 的关键一步。

### 15. Event Segmentation Theory (EST)
- **文献标识**：Zacks, Speer, Swallow, Braver & Reynolds, *Psychological Bulletin* 2007
- **1. 核心解决的问题**：人类面对的感官输入本质上是连续不断的时间流（视觉、听觉、体感没有天然分割线），为什么人类却能清晰回忆出“刚才那件事”和“上一件事”而不是糊成一团？
- **2. 使用的方法**：通过认知心理学实验与神经机制理论，阐述大脑在持续运行**事件模型（Working Event Models）**预测下一刻感官输入：只要当前场景可被稳定预测就维持同一事件；一旦**预测误差（Prediction Error）骤升**（空间切换、人物变化、目标/意图改变、长时间中断），系统即触发一次瞬态更新（Event Boundary），将刚刚结束的一段感知封装定型送入长期记忆。
- **3. 解决前后的对照**：
  - **Before**：把持续信息流看作均匀时间切片或靠主观拍脑袋定义“一件事”，找不到可计算的自动切分依据。
  - **After**：揭示了**“预测误差驱动边界切分”**这一跨模态通用原理，直接启发了 17 年后的 `EM-LLM`、`Nemori` 等大模型情景分割算法。
- **4. 对「Context 补全计划」的提示与指示**：
  - **这是本项目多渠道聚合层的“第一性原理”**：把 12 个分散通道揉成一个个有意义的 `Episode`，不需要等晚上让 LLM 硬读全部原始流水账——当**“AFK 间隙超过阈值 / 活跃窗口切换到完全不同的 Workspace / 录音说话人或主题突变”**这些特征同时出现时，就已经抓住了天然的高置信事件边界。

### 16. MyLifeBits & Lifelog Search Challenge (LSC)
- **文献标识**：Gemmell, Bell & Lueder, *Communications of the ACM* 2006 · http://lifelogsearch.org/
- **1. 核心解决的问题**：早在 2000 年代初由 Gordon Bell 亲自试验：“如果把一个人一生读过的文章、拍过的照片、电话录音、书信和网页**全部数字化留存**下来，究竟需要面对哪些存储、索引、标注与瞬间检索挑战？”
- **2. 使用的方法**：`MyLifeBits` 作为史上最经典的终身数字记忆实验系统，提出了针对海量多模态个人数据的持久唯一 ID、多属性分类与关联链接模型；而自 2018 年延续至今的国际竞赛 **Lifelog Search Challenge (LSC)** 则把可穿戴相机+位置+生物/数字日志做成年度交互检索基准，不断验证时间轴浏览、混合检索与多模态人机交互检索策略。
- **3. 解决前后的对照**：
  - **Before**：终身全量留存个人数据还停留在范尼瓦尔·布什《Memex》的哲学设想阶段，缺乏真实数十万级异构个人文件的长期系统实验。
  - **After**：用二十年实践反复证明：**“全量采下来”只是起点，真正的难点在极低成本的自动索引、跨模态时间与实体联动、以及 10 秒内定位目标记忆的交互机制**。
- **4. 对「Context 补全计划」的提示与指示**：
  - **少走二十年弯路的核心警示——“Read-only Archive（只写不读的数据坟墓）”是个人 Lifelog 项目最大的死因**：每多接一个传感器前，先问清楚这个通道能以什么结构进入 L1、如何低延迟被 LLM 或人秒级查到、以及如何安全清理过期垃圾，避免硬件和隐私负担反噬日常使用。

### 17. Effective context engineering for AI agents
- **出处与链接**：Anthropic Engineering · https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
- **1. 核心解决的问题**：随着 Agent 从单轮对话走向长时间运行的多工具自主循环，工程团队往往沿用“静态写死一条超长 Prompt 或一股脑 RAG 塞满上下文”的旧思维，结果 Token 迅速膨胀且模型注意力被海量无关历史稀释。
- **2. 使用的方法**：正式主张从“Prompt Engineering”升级为 **“Context Engineering（上下文工程）”**：强调**在有限的注意预算下筛选“最小高信号 Token 集合（Smallest possible set of high-signal tokens）”**，并系统总结长程 Agent 的四类核心手段——**动态上下文精简与压缩（Compaction）、结构化外部笔记（Structured Note-taking / Scratchpad）、按需即时检索加载（Just-in-Time Retrieval via tools）以及多子智能体上下文隔离（Sub-agent Isolation）**。
- **3. 解决前后的对照**：
  - **Before**：误以为模型支持 200K/1M 窗口就能把所有日记、文件、聊天原封不动全塞进去“让模型自己看”。
  - **After**：清晰建立了以**信噪比、按需加载与即时摘要**为核心的工程规范，Context 成了像内存带宽一样需要精心调度的稀缺系统资源。
- **4. 对「Context 补全计划」的提示与指示**：
  - **彻底确立了我们项目的存在意义与工具契约设计**：我们的本地 Context 底座就是外部结构化记忆 + 按需检索服务端（MCP）；**不要把整天录音稿直接倒进用户工作对话**，而是给 Agent 一组高信噪比摘要卡与按需读取细节的工具（Just-in-Time Retrieval）。

### 18. Context Rot: How Increasing Input Tokens Impacts LLM Performance
- **出处与链接**：Chroma Technical Report · https://research.trychroma.com/context-rot
- **1. 核心解决的问题**：大模型厂商宣传百万级上下文窗口时，用户往往盲目相信“把全部历史拼在 Prompt 里效果不会变差（甚至更好）”，缺乏对长上下文中真实推理可靠性退化的实证认知。
- **2. 使用的方法**：通过一系列受控长上下文实验（改变输入长度、干扰项/Distractor 数量、答案位置与语义相似度混淆度），在多个主流闭源与开源模型上评测多类检索、推理与复制任务表现，观察输入长度增加带来的性能曲线变化。
- **3. 解决前后的对照**：
  - **Before**：流行一种偷懒暴论：“长窗口越来越大，Context 压缩、RAG 和记忆分层快过时了，全部 Raw Text 直接硬喂即可。”
  - **After**：实证表明即便任务本身远低于模型宣称的最大窗口上限，只要输入无关上下文增多或存在相似干扰项，绝大多数模型的表现都会明显退化（即 **Context Rot，上下文腐烂**）。
- **4. 对「Context 补全计划」的提示与指示**：
  - **为“多渠道原始数据必须分层蒸馏 + 按需精选注入（L0→L4）”提供了最硬核的反面论据**：哪怕将来模型支持一千万 Token，把一周的冗长口水录音、上千条剪切板碎片段和杂乱网页直接塞给 Agent，只会诱发 Context Rot 拉低智力；**先去噪、先聚合 Episode、再精确召回**永远是高智能上限的刚需。

### 19. HPI / Promnesia / Exobrain 系列工程文章

  - **克制过度设计（Anti-Overengineering）的定海神针**：本项目先聚焦少数最稳的真数据源（音频 `record-for-agent` + 剪切板 `ClipContext` + 浏览器有效停留 + 窗口焦点），L0 原始归档坚决保持不可变与可读性，确保十年后换了新 AI 模型数据资产依然毫发无损。

### 20. Personal Data Warehouses: Reclaiming Your Data
- **出处与链接**：Simon Willison · https://simonwillison.net/2020/Nov/14/personal-data-warehouses/
- **1. 核心解决的问题**：用户产出的全部数字活动记录分散在各大互联网公司的私有 SaaS 后台里，想把它们变成自己可查询、可组合的个人资产，技术门槛究竟卡在哪里？
- **2. 使用的方法**：提出并普及 **“以单个 SQLite 文件为核心、围绕轻量 CLI 采集器 + Datasette 可视化探查的个人数据仓库（Personal Data Warehouse）”** 范式——把复杂的大数据平台微缩为一个零运维单文件生态。
- **3. 解决前后的对照**：

  - **After**：证明仅凭 `*-to-sqlite` 小脚本 + SQLite 视图/FTS5 + Datasette，单人周末即可跑通极高可用度的个人数据仓库。

### 21. nspasteboard.org 与 macOS 15.4+ `NSPasteboard.accessBehavior` 剪贴板规范
- **出处与链接**：http://nspasteboard.org/ · https://developer.apple.com/documentation/appkit/nspasteboard · https://mjtsai.com/blog/
- **1. 核心解决的问题**：如果桌面端上下文采集工具不分青红皂白静默读取并持久化系统剪贴板，不仅会意外落盘密码管理器里的账号密码、双重验证码与瞬态密钥，在现代 macOS 版本中还会持续触发系统权限弹窗或遭到系统拦截。
- **2. 使用的方法**：结合社区事实标准 **`nspasteboard.org` 特殊剪贴板类型标记**（如 `org.nspasteboard.ConcealedType` 机密内容、`org.nspasteboard.TransientType` 瞬态内容、`org.nspasteboard.AutoGeneratedType` 自动生成内容）以及 Apple macOS 15.4+ 引入的 **`NSPasteboard.accessBehavior` / 隐私访问控制与来源校验规范**，做到合规检测、及时过滤敏感数据并引导正确授权。
- **3. 解决前后的对照**：
  - **Before**：剪贴板采集器一不小心就把 1Password 复制的密钥明文存进上下文日志发给大模型，成为高危安全漏洞；同时升级新版 macOS 后静默读取体验频繁被弹窗打断。
  - **After**：在采集源头即完成敏感凭证零落盘拦截，并与最新 macOS 平台权限模型保持一致。
- **4. 对「Context 补全计划」的提示与指示**：
  - **`ClipContext` 及后续桌面采集端的强制工程红线（Must-Have Guardrail）**：必须在事件写入 L0 之前显式检查 `ConcealedType` / `TransientType` 与主流密码管理器/敏感应用黑名单（App Exclusion List），同时适配 macOS 15.4+ 剪贴板访问策略与状态检查，绝不靠绕过系统权限采集数据。

### 22. 浏览器有效停留三层信号规范（Chrome `idle` + `windows.onFocusChanged` + MDN `Page Visibility API`）
- **出处与链接**：https://developer.chrome.com/docs/extensions/reference/api/idle · https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API
- **1. 核心解决的问题**：单纯靠记录 `tabs.onUpdated` / `history.onVisited` 来采集网页上下文会产生巨量垃圾噪音——人开着 40 个后台标签页或切出去吃饭挂机 3 小时，如果算成“深度阅读 3 小时”，会彻底污染用户的注意力画像与检索排序。
- **2. 使用的方法**：结合浏览器原生三层正交信号联合判定**“真实有效的注意力停留（Active Dwell Time）”**：
  1. `Page Visibility API`（标签页当前处于可见前台 `visible`，而非后台隐藏页）；
  2. `chrome.windows.onFocusChanged`（浏览器窗口本身当前处于操作系统聚焦状态，人不是在用别的 IDE 或切走了）；
  3. `chrome.idle` API（键鼠/屏幕活动处于 `active`，而非系统锁屏或长时间无操作 `idle/locked`）。
- **3. 解决前后的对照**：
  - **Before**：一个随手点开却切到后台放了半天的标签页被误标为重要学习内容，真正专注查文档精读 3 分钟的页面却淹没在海量瞬时跳转记录里。
  - **After**：只有同时满足“前台可见 + 窗口聚焦 + 用户未 Idle”的连续时间累计超过有效阈值（或主动发生复制/高亮动作）的页面，才触发正文抽取（Defuddle/Readability）并计入高信噪比浏览上下文。
- **4. 对「Context 补全计划」的提示与指示**：
  - **未来接入浏览器采集扩展的精确判定标准**：把“打开了 URL”降级为原始噪声信号，把“三层信号交叉验证后的有效阅读区间（Active Reading Span）”作为触发正文 Markdown 归档和进入 L1 `ContextEvent` 的闸门，能直接砍掉绝大部分浏览噪声并大幅节省后续 LLM 处理成本。
